# 工程笔记

将输入材料整理为一份独立、可复用、可落实的工程笔记。让读者一眼看清结论与实现路径，细读后能确认公式前提、数据链路、边界条件和验收方式。

## 写作立场

- 将笔记视为独立的工程知识载体，而不是项目开发记录、代码说明书、问题对话纪要或测试日志摘录。
- 保留对工程决策有用的理论推导、约定、约束和检查点；删除仅服务于当下项目的偶然细节。
- 用户提供既有笔记作为示范时，只提炼其章节层次、推导密度、语气、信息取舍和边界意识；不要扩展阅读相关代码，也不要把示范笔记中的项目实现还原到新笔记。
- 使用专业、肯定、可执行的陈述。不要保留“我认为”“你可以”“刚才讨论”“当前代码里”等对话痕迹。
- 只有在用户明确要求时才写入产品型号、具体数值、厂商、协议或文件路径；即使写入，也说明其适用边界，不将其伪装成普适规律。

## 硬性边界

### 不耦合代码

除非用户明确要求“代码设计说明”，否则禁止在笔记正文中写入或暗示以下内容：

- 文件、目录、模块、任务、类、接口、宏、变量、函数、寄存器和调用顺序；
- 源码片段、伪代码、构建命令、调试命令、串口/RTT 原始日志；
- “调用某函数”“读取某变量”“在某中断中”等实现绑定表述；
- 某个工程独有的命名、状态机名称、日志字段、开关名称与魔法数。

需要交代落地方式时，只描述通用的数据与控制链路，例如“在固定周期的后台测量窗口采集”“由控制器已计算的 dq 量构造观测量”“结束后进行带截距回归”。不要把这类描述还原成代码结构。

### 不牺牲理论

- 每个核心结论都必须有最短充分的理论解释或推导；不要仅给经验结论或公式结论。
- 只保留能连接“物理模型 → 可观测量 → 目标参数”的公式。不要堆砌教材级基础公式。
- 对每个核心公式说明其用途、变量物理含义、单位或标幺约定，以及成立条件；必要时说明不满足条件时应如何重新确认系数或模型。
- 使用单个 `$...$` 包裹行内和独立 LaTex 公式。不要混用反斜杠形式或双美元符号。

### 不发散

- 不引入与主题无关的背景史、行业综述、替代方案罗列或泛泛建议。
- 不把验证内容扩展为完整测试计划；只留下影响结论可信度的关键筛选、对照和验收点。
- 不把“实际使用”写成逐条操作教程，也不重复理论章节已解释的内容。
- 在原始材料存在不确定性时，显式写出假设、待确认量和失效边界；不要擅自补全关键硬件、控制或标定条件。

## 组织方式

按以下层次组织，删除不适用的小节，不为凑模板保留空内容。

1. `# 主题`
2. `## 结论`：说明解决什么、产出哪些参数/判据、适用范围与不包含什么。
3. `## 理论依据`：从最贴近目标的模型开始，推导到可计算的目标关系；把变换约定、单位和关键前提紧跟在公式后。
4. `## 初值或量级校验`：仅在存在独立的铭牌、经验或数据表校验时保留；明确它不是最终结果。
5. `## 需要的观测量`：用简洁表格列出量、用途、要求或来源。
6. `## 实施流程`：按“准备 → 激励/工况 → 稳态采样 → 单点诊断 → 全局估计 → 输出”描述最小闭环。
7. `## 数据筛选与验收`：列出无效数据条件、拟合或统计策略、交叉检查及通过标准。
8. `## 实际使用`：仅在用户提供了已验证的工程流程或测试链条时保留。用概念性语言说明采样节奏、窗口统计、最终输出和记录项。
9. `## 结果记录`：列出需长期保存的参数、单位、工况、筛选策略与版本依据。

将“结论—理论—观测—流程—验收”保持为主干。若主题不涉及参数估计，可将“单点诊断/全局估计”替换为相应的计算、设计或验证环节，但保持从依据到落地的因果链。

## 公式与量纲检查

1. 从目标量倒推可观测量，先写出包含目标量的最简工程模型。
2. 仅做必要移项、线性化或统计变换，明确这样做消除了何种不可观测项或固定误差。
3. 在首次出现时声明坐标系、电流/电压峰值或 RMS、幅值不变或功率不变变换、线电压或相电压、机械量或电气量等约定。
4. 将系数与单位核对到最终目标量；遇到跨厂商公式时，先限定其电压、电流和 $K_V$ 定义，再把它定位为初值或量级校验。
5. 区分“原始测量量”“坐标变换后的控制量”“窗口统计量”“最终估计量”。不要把 dq 量笼统称为相电流或相电压，也不要把数值相等误写为物理量完全相同。

## 实现链条的表达

将实现写成可迁移的工程链，而非软件实现细节：

- 明确前置条件：工况、传感器、控制闭环、标定状态和安全限制。
- 给出激励的维度：速度、电流、频率、载荷、温度或其他与主题相关的覆盖范围；必要时使用正反向或重复试验抑制偏差。
- 说明每个窗口累计什么量、何时判断稳态、何时丢弃样本、何时形成单点诊断值。
- 区分单点诊断与最终估计：单点用于发现异常，全局回归或统计值用于输出最终参数。
- 说明最终输出的名称、物理意义、单位和建议有效数字；同时列出应随结果保存的工况与质量信息。

## 成文前检查

逐项检查并修正：

- 是否在开头给出了目标、适用范围和非目标？
- 是否存在从物理模型到最终量的短而完整的推导？
- 每个系数是否与单位、峰值/RMS、线/相、机械/电气和坐标变换约定一致？
- 是否把设备数据、经验换算与正式辨识/计算结果清楚分级？
- 是否已给出最小观测量、实施闭环、无效条件和验收对照？
- 是否删除了所有代码标识符、文件路径、日志、对话措辞及项目专有实现细节？
- 是否删除了重复解释、无关知识和看似全面但不可执行的建议？

输出时只交付完成后的 Markdown 文件，放在当前文件夹目录下，不要直接在窗口输出；除非用户要求，不额外附带写作过程、代码映射或格式说明。
