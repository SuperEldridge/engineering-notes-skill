# 工程笔记 Skill

> 将理论推导、工程链条与验收边界凝练为独立、简洁、可复用的工程技术笔记。

适用于控制算法、嵌入式系统、电机、电子、电气、机械、测试、参数辨识等工程主题。

核心目标不是记录“项目怎么写的”，而是回答：

**为什么这样做、需要什么数据、如何实施、什么条件下结论才成立。**

---

## 适用场景

- 将零散技术讨论整理成正式工程笔记
- 将项目经验提炼为可复用的方法
- 整理控制算法、参数辨识和测试方法
- 审查已有工程笔记的理论与工程完整性
- 从复杂材料中提炼结论、公式、观测量和实施流程
- 去除代码、日志和项目上下文，只保留可迁移的工程知识

---

## 写作结构

根据主题需要组织内容，不强制保留无意义章节。

通常按照以下主线展开：

```text
结论
 ↓
理论依据
 ↓
需要的观测量
 ↓
实施流程
 ↓
数据筛选与验收
 ↓
结果记录
```

核心是保持：

> **结论 → 理论 → 观测 → 流程 → 验收**

之间完整的因果链。

---

## 写作原则

### 独立

笔记应当脱离原项目后仍然可以阅读和使用。

不会依赖：

- 文件名
- 模块名
- 类、函数、变量
- 寄存器
- 调用顺序
- 调试命令
- 原始日志
- 项目专有状态机或命名

除非明确要求编写代码设计说明。

### 有理论依据

核心结论必须有足够的理论解释。

公式只保留能够连接：

```text
物理模型 → 可观测量 → 目标参数
```

的必要部分。

同时明确：

- 变量物理意义
- 单位
- 坐标系
- 峰值 / RMS
- 线量 / 相量
- 机械量 / 电气量
- 公式成立条件

### 可落地

不仅说明“是什么”，还要说明工程上如何得到结果。

包括必要的：

- 前置条件
- 激励或工况
- 观测量
- 稳态条件
- 数据筛选
- 单点诊断
- 全局估计或统计
- 验收标准

### 不发散

不会为了显得完整而加入：

- 无关背景历史
- 行业综述
- 大量替代方案
- 教材级基础知识
- 与结论无关的测试项目
- 没有依据的工程建议

材料中存在不确定性时，会明确写出假设、待确认量和失效边界，而不是自行补全。

---

## 公式与量纲检查

对于涉及计算或参数辨识的内容，会重点检查：

- 目标量是否能由观测量得到
- 推导过程是否完整
- 系数是否正确
- 单位是否一致
- 峰值与 RMS 是否混用
- 线电压与相电压是否混用
- 机械量与电气量是否混用
- 坐标变换约定是否明确
- 原始测量量、控制量、统计量和最终估计量是否被正确区分

设备数据、经验换算和正式计算结果也会明确区分，不把量级估算当成最终结论。

---

## 使用方式

手动调用：

~~~text
使用 $engineering-notes 将这些材料整理成独立、简洁且可落地的工程笔记。
~~~

也可以直接说明目标：

~~~text
使用 $engineering-notes 整理这份参数辨识方案。

保留必要的理论推导、观测量、实施流程和验收方法，
去掉代码、变量名、日志和当前项目专有内容。
~~~

该 Skill 默认不会隐式调用，需要用户主动触发。

---

## 输出特点

最终笔记应当做到：

- 开头直接给出结论和适用范围
- 理论推导短而完整
- 公式前提和量纲明确
- 观测量足够且没有冗余
- 实施流程能够形成最小工程闭环
- 数据筛选和验收标准明确
- 不包含无关代码实现细节
- 不依赖当前项目上下文
- 可以作为独立工程知识长期保存
